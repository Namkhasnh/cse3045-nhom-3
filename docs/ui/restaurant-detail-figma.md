# Restaurant storefront and compact buyer footer

User approved October 24, 2026: [Restaurant Detail Figma Make](https://www.figma.com/make/XymiDbnoGxZqEB2oY2bP45/Redesign-Restaurant-Detail-Page), including owner-managed cover/introduction, a cart drawer and compact footer on buyer pages. This extends US03/US05/US12; it does not authorize a production migration or deployment.

## Presentation

- `/restaurants/{id}` uses a 1200px content area, ivory surface, 24px photographic hero, dark scrim, current restaurant name/introduction/status/hours/address and a back link. Be Vietnam Pro and the existing header remain.
- The default hero is the exact photo URL used by the Make's `Hero`: Unsplash `photo-1628430043154-290c67c19550`, crop1800×900, quality85. Its local asset is `frontend/public/images/restaurant/default-cover.jpg`; label it “Ảnh minh họa”. An invalid/unavailable uploaded image falls back to this image, then to an illustration if the local image also fails.
- Empty introduction uses the approved Make copy: “Món ngon quen thuộc, giá sinh viên, phục vụ nhanh tại Hòa Lạc.” It is a presentation default, not persisted historical restaurant information.
- Menu search preserves the API's name-prefix semantics; real category chips, native price selection, reset, cursor pagination and retry remain connected. Desktop/tablet/mobile grids use3/2/1columns. Sold-out dishes remain visible with disabled add actions.
- No prototype rating, notification total, invented cuisine category, collection-at-restaurant option, discount or delivery-time estimate is introduced. Actual dish images remain dynamic; missing ones show the existing fallback.
- Skeleton, missing restaurant, network error, empty menu/results, closed/not-accepting, long text, reduced motion and keyboard states are supported. Hero height can grow for long user content.
- Buyer routes use a charcoal compact footer with small brand/tagline, implemented discovery/support links and copyright. Desktop target140–200px; mobile wraps naturally. Owner/Admin management layouts retain the previous footer. A manager browsing as a buyer receives the buyer footer.

## Cart drawer

The header cart control on restaurant-detail routes and the floating “Xem giỏ” button open the same native modal drawer. Add actions announce the existing cart notice and never force the drawer open. CartProvider remains the only cart draft source; quantity/removal, cross-tab/reload persistence and restaurant-switch consent are unchanged.

The drawer displays accepted prices and exact BigInt subtotals. It warns about current price/availability changes and unknown delivery fees; `/cart` remains the route for delivery selection, explicit price consent and continuing checkout. Escape/backdrop/close dismiss; native modal focus containment, focus restoration and body-scroll locking apply. There is no new order/payment mutation.

## Owner content contract

The cài đặt quán form allows introduction editing and JPEG/PNG upload, replacement, preview or returning to the default image. Pending changes are previewed locally and retained on save failure. Other settings saves/reloads preserve dirty content fields. Success is shown only after the backend confirms PATCH.

`description` is nullable, trimmed plain text, at most2000Unicode code points/8000UTF8bytes. Null/blank selects the default. `cover_image_reference` is nullable and accepts only `/api/v1/restaurant-cover-media/{id}` generated by the backend. Owner PATCH retains required `expected_version`; stale edits409 require reload and deliberate resubmission. Admin PATCH does not gain content-write permissions.

Public restaurant and owner/admin detail DTOs add these two nullable fields. The [October26 imagery extension](restaurant-images.md) adds a separate optional avatar, owner storefront link and crop editor. They do not enter accepted order snapshots or affect profile/readiness requirements.

| --- | --- |
| POST `/owner/restaurants/{id}/cover-media` | Active current owner; JSON `mime_type/content_base64`;201metadata `{id,image_reference,mime_type,size_bytes,width,height}`. Image reads use actual MIME, nosniff and no-store. Preview errors never become upload/save success. Full machine schemas extend [setup OpenAPI](../data/setup.openapi.json) and [public catalog OpenAPI](../data/openapi.yaml).

## Persistence and storage

Forward migration `20261024010000_restaurant_storefront` adds nullable restaurant `description/cover_media_asset_id` and a separate `restaurant_cover_media` table. Existing rows receive NULLs. Same-restaurant composite FK and image/text CHECKs enforce storage bounds. Metadata is owned by media, profile fields by restaurants; workflow coordinates their public services under account→restaurant→asset locks and audits content-change booleans without storing text/image bytes in audit.

Cover objects reuse the configured private local media bucket with a distinct `covers/` prefix; dish cleanup cannot claim them. Storage I/O is outside retried transactions. Upload acknowledgement loss checks metadata before compensation. Replacement/null requests cleanup transactionally, then reference-checked claims and external deletion happen after commit; failed deletion is retryable. A claimed image cannot reattach.

The existing guarded `media:cleanup:local` command now also cleans superseded/unattached covers (unused uploads age24h), plus untracked `covers/` orphans older than24h. It still refuses retained/non-test/nonlocal targets. Runtime grants permit content updates, metadata INSERT and lifecycle-marker UPDATE only; object identity and deletion of metadata remain denied. Production storage/scheduling remains under DEC-10.
